# Requirements Document

## Project Description (Input)

### プロジェクト概要
Google Cloud Platform上でCloud Run Functions（第2世代）を使用し、PythonとPlaywrightでcarewellというWebサービスを自動操作して、対象ファイルを取得し、Google Driveへの保存とスプレッドシートへの記録を行う自動化システム。

### 環境
- **プラットフォーム**: Google Cloud Platform
- **実行環境**: Cloud Run Functions (2nd gen)
- **言語**: Python
- **ブラウザ自動化**: Playwright (ヘッドレスモード)
- **GCPプロジェクト情報**:
  - アカウント: system@jaccw.or.jp
  - プロジェクト名: carewell-automation
  - プロジェクト番号: 61759806259
  - プロジェクト ID: carewell-automation

### 主要機能
1. **Carewell Webサービスの自動操作**
   - ログイン認証（ユーザーID/パスワード）
   - クラス管理画面への遷移
   - 教科クラス一覧から対象クラスの選択
   - レポート採点画面での課題選択
   - 提出ファイル一覧の取得
   - ファイルのダウンロード

2. **データ管理**
   - 取得済みファイルの重複チェック（Firestoreで管理）
   - Google Driveへのファイル保存
   - スプレッドシートへのメタデータ記録

3. **セキュリティ**
   - Secret Managerでの認証情報管理
   - サービスアカウントでのGoogle API認証
   - 詳細なロギング（トレーサビリティ確保）

4. **実行制御**
   - Cloud Schedulerによる定期実行（30分間隔）
   - 複数パターンの処理（クラス×課題の組み合わせ）
   - エラーハンドリングとメール通知

### 処理フロー詳細
1. Carewellログイン (https://jaccw-carewel.study.jp/)
2. 「クラス管理」をクリック
3. 「教科クラス一覧」をクリック
4. 対象クラス（パラメータ指定）を選択
5. 「レポート採点」をクリック
6. 対象課題（パラメータ指定）を選択
7. 「全て」タブをクリック
8. 提出者一覧テーブルを取得
9. 未取得ファイルについて:
   - 提出者リンクをクリック
   - ダウンロードファイルを取得
   - Google Driveに保存
   - Firestoreに記録
   - スプレッドシートに追記
   - 「レポート選択」へ戻る
10. ページネーション処理（全ページ対応）
11. 全ファイル取得完了で終了

### データ構造
**Firestore**:
- コレクション構造: `{クラス名}/{課題名}/documents`
- ドキュメントフィールド:
  - 複合キー（日介番号 + 提出日）
  - 氏名
  - 日介番号
  - 提出日
  - ファイル名
  - ファイルURL
  - ダウンロード日時

**スプレッドシート**:
- クラス名ごとに別スプレッドシート
- 課題名ごとに別シート
- カラム: 複合キー、氏名、日介番号、提出日、ファイル名、ファイルURL、ダウンロード日時

### パラメータ設定
Cloud Schedulerから渡されるパラメータ:
- クラス名（例: "令和7年度 デジタル中核人材養成研修 №01"）
- 課題名（例: "課題①業務分析　※～11/3〆切"）
- Google DriveフォルダーID
- スプレッドシートID

### 実行パターン
- クラス数: 7パターン
- 課題数: 可変（各クラスで複数）
- 実行頻度: 30分ごと（スケジューラーでタイミング調整）

### エラーハンドリング
- Playwright操作失敗時のリトライ
- 詳細ログ出力
- エラー時のメール通知（Gmail API経由、宛先: hy.unimail.11@gmail.com）

### Secret Manager管理対象
- `carewell-user-id`: Carewellログイン用ユーザーID
- `carewell-password`: Carewellログイン用パスワード
- Gmail API認証情報

### ファイル形式
PDF、CSV、画像、Excel、PowerPointなど多様な形式に対応

## Requirements

### 要件1: Carewell Webサービスへの認証とナビゲーション
**目的:** システム管理者として、Carewell Webサービスに安全に認証し、対象のレポート採点画面に自動的にナビゲートできるようにすることで、手動操作なしでファイル取得処理を実行できるようにする

#### 受入基準
1. WHEN 自動化システムが起動される THEN システムはSecret Managerから認証情報（carewell-user-id、carewell-password）を安全に取得しなければならない
2. WHEN 認証情報が取得される THEN システムはPlaywrightヘッドレスブラウザでhttps://jaccw-carewel.study.jp/にアクセスしなければならない
3. WHEN ログイン画面が表示される THEN システムは指定されたフォーム要素（ctl00$masterMain$txtUserID、ctl00$masterMain$txtPassword）に認証情報を入力しなければならない
4. WHEN 認証情報が入力される THEN システムはログインボタン（ctl00$masterMain$btnSubmit）をクリックしなければならない
5. IF ログインが成功する THEN システムはフレーム内の「クラス管理」リンクを検索してクリックしなければならない
6. WHEN 画面遷移が完了する THEN システムは「教科クラス一覧」リンク（target="list"のframe内）を検索してクリックしなければならない
7. WHEN 教科クラス一覧が表示される AND データベースからの動的読み込みが完了する（3-10秒待機） THEN システムはパラメータで指定されたクラス名に一致するリンク要素を検索しなければならない
8. IF 対象クラスが見つかる THEN システムはそのクラスリンクをクリックして詳細画面に遷移しなければならない
9. WHEN クラス詳細画面が表示される THEN システムは「レポート採点」リンクを検索してクリックしなければならない
10. WHEN レポート採点画面が表示される THEN システムはパラメータで指定された課題名に一致するリンク要素を検索してクリックしなければならない
11. IF 認証に失敗する OR ナビゲーション中に要素が見つからない THEN システムはエラーログを出力し、最大3回までリトライしなければならない

### 要件2: 提出ファイル一覧の取得と重複チェック
**目的:** システム管理者として、課題の全提出者リストを取得し、既に処理済みのファイルをスキップできるようにすることで、重複ダウンロードを防止し効率的な処理を実現する

#### 受入基準
1. WHEN レポート課題画面に到達する THEN システムは「全て」タブリンクを検索してクリックしなければならない
2. WHEN 「全て」タブがクリックされる THEN システムは数秒待機してデータベースからのデータ取得完了を待たなければならない
3. WHEN データ表示が完了する THEN システムは提出者一覧テーブル（standard_grid_item クラス）を検索して全行を取得しなければならない
4. WHEN テーブル行が取得される THEN システムは各行から以下の情報を抽出しなければならない: 氏名、日介番号、提出日（ctl00_masterMain_gvwMain_ctl*_lblStudyDate）、リンクURL
5. WHEN 提出者情報が抽出される THEN システムは日介番号と提出日を連結して複合キーを生成しなければならない（例: "N9903754_20251002095045"）
6. WHEN 複合キーが生成される THEN システムはFirestoreの該当コレクション（{クラス名}/{課題名}/documents）に複合キーのドキュメントが存在するか確認しなければならない
7. IF 複合キーがFirestoreに存在する THEN システムはその提出者をスキップして次の行を処理しなければならない
8. IF 複合キーがFirestoreに存在しない THEN システムはその提出者を未処理リストに追加しなければならない
9. WHEN 現在ページの全行が処理される THEN システムはページネーションセレクト要素（ctl00$masterMain$dpgMain$dpgMain$ctl00$ddlPage）の存在を確認しなければならない
10. IF 次のページが存在する THEN システムは次のページ番号を選択してページ遷移し、同じ処理を繰り返さなければならない
11. WHEN 全ページの処理が完了する THEN システムは未処理リストを返さなければならない

### 要件3: ファイルのダウンロードとGoogle Driveへの保存
**目的:** システム管理者として、未処理の提出ファイルを自動的にダウンロードし、指定されたGoogle Driveフォルダに保存できるようにすることで、ファイルの一元管理を実現する

#### 受入基準
1. WHEN 未処理提出者リストが存在する THEN システムは各提出者について順次処理を実行しなければならない
2. WHEN 提出者を処理する THEN システムは提出者の氏名リンク（例: ctl00_masterMain_gvwMain_ctl*_hplLoginID）をクリックしなければならない
3. WHEN 提出者詳細画面に遷移する THEN システムはフレーム内のダウンロードリンク（例: download.aspx?id=*）を検索しなければならない
4. WHEN ダウンロードリンクが見つかる THEN システムはリンクテキストからファイル名を取得しなければならない
5. WHEN ファイル名が取得される THEN システムはダウンロードリンクをクリックしてファイルをローカル一時ディレクトリに保存しなければならない
6. IF ファイルが正常にダウンロードされる THEN システムはサービスアカウント認証でGoogle Drive APIに接続しなければならない
7. WHEN Google Drive APIに接続される THEN システムはパラメータで指定されたフォルダIDにファイルをアップロードしなければならない
8. WHEN アップロードが完了する THEN システムはアップロードされたファイルの共有URLを取得しなければならない
9. IF アップロードに失敗する THEN システムはエラーログを出力し、最大3回までリトライしなければならない
10. WHEN ファイル処理が完了する OR 失敗が確定する THEN システムはローカル一時ファイルを削除しなければならない
11. WHILE ファイル処理を実行している THE システムは各ステップの詳細ログ（ファイル名、サイズ、タイムスタンプ）を出力しなければならない
12. WHEN 各提出者の処理が完了する THEN システムは「レポート選択」へ戻るリンク（list.aspx?course_id=*&unit_id=*&filter=*）をクリックして一覧画面に戻らなければならない

### 要件4: Firestoreへのメタデータ記録
**目的:** システム管理者として、処理済みファイルのメタデータをFirestoreに記録できるようにすることで、重複チェックとトレーサビリティを確保する

#### 受入基準
1. WHEN ファイルがGoogle Driveにアップロードされる AND 共有URLが取得される THEN システムはFirestoreにドキュメントを作成しなければならない
2. WHEN Firestoreドキュメントを作成する THEN システムは以下の階層構造を使用しなければならない: コレクション名={クラス名}/{課題名}/documents
3. WHEN ドキュメントを保存する THEN システムは以下のフィールドを含めなければならない:
   - composite_key: 日介番号と提出日の複合キー
   - name: 氏名
   - care_number: 日介番号
   - submitted_at: 提出日（ISO 8601形式）
   - file_name: ファイル名
   - file_url: Google DriveファイルURL
   - downloaded_at: ダウンロード日時（ISO 8601形式）
4. WHEN ドキュメントを保存する THEN システムはドキュメントIDとして複合キーを使用しなければならない
5. IF Firestoreへの書き込みに失敗する THEN システムはエラーログを出力し、最大3回までリトライしなければならない
6. IF 3回のリトライ後も失敗する THEN システムは当該ファイルを失敗リストに追加し、次のファイル処理に進まなければならない

### 要件5: スプレッドシートへのデータ反映
**目的:** システム管理者として、処理済みファイルの情報をGoogle Sheetsに記録できるようにすることで、人間が読みやすい形式でデータを確認できるようにする

#### 受入基準
1. WHEN Firestoreへのデータ保存が成功する THEN システムはGoogle Sheets APIに接続しなければならない
2. WHEN Google Sheets APIに接続される THEN システムはパラメータで指定されたスプレッドシートIDを開かなければならない
3. WHEN スプレッドシートが開かれる THEN システムは課題名に対応するシート名を検索しなければならない
4. IF 対象シートが存在しない THEN システムは新しいシートを作成し、ヘッダー行（複合キー、氏名、日介番号、提出日、ファイル名、ファイルURL、ダウンロード日時）を追加しなければならない
5. IF 対象シートが存在する THEN システムは次の空白行を特定しなければならない
6. WHEN 書き込み位置が特定される THEN システムは以下のデータを行として追加しなければならない: composite_key、name、care_number、submitted_at、file_name、file_url、downloaded_at
7. IF スプレッドシートへの書き込みに失敗する THEN システムはエラーログを出力し、最大3回までリトライしなければならない
8. WHILE スプレッドシート操作を実行している THE システムは各操作の詳細ログを出力しなければならない

### 要件6: セキュリティとシークレット管理
**目的:** システム管理者として、機密情報を安全に管理できるようにすることで、セキュリティベストプラクティスに準拠したシステムを実現する

2. WHEN Secret Managerにアクセスする THEN システムは以下のシークレット名を使用しなければならない:
   - carewell-user-id

3. WHEN Google Drive/Sheets APIを使用する THEN システムはサービスアカウント認証を使用しなければならない
4. WHEN サービスアカウントを使用する THEN システムはサービスアカウントキーJSONをSecret Managerから取得しなければならない
5. WHILE システムが実行されている THE システムは機密情報（パスワード、APIキー）をログに出力してはならない
6. WHEN ログを出力する THEN システムは機密情報をマスキング（例: "password: ***"）しなければならない
7. WHEN 一時ファイルを作成する THEN システムは処理完了後に必ず削除しなければならない

### 要件7: エラーハンドリングと通知
**目的:** システム管理者として、システムエラーを迅速に検知し対応できるようにすることで、システムの信頼性と保守性を向上させる

#### 受入基準
1. WHEN システムで予期しないエラーが発生する THEN システムは詳細なエラーログ（スタックトレース、発生時刻、コンテキスト情報）を出力しなければならない
2. WHEN Playwright操作でタイムアウトまたは要素未検出が発生する THEN システムは最大3回までリトライしなければならない
3. WHEN 3回のリトライ後も失敗する THEN システムはエラー詳細を記録し、次の処理に進むか実行を終了しなければならない
4. IF 以下のクリティカルエラーが発生する THEN システムはGmail API経由でhy.unimail.11@gmail.comにエラー通知メールを送信しなければならない:
   - 認証失敗
   - Secret Manager接続失敗
   - 連続する複数ファイルのダウンロード失敗
   - Firestore/Sheets API接続失敗
5. WHEN エラー通知メールを送信する THEN システムは以下の情報を含めなければならない: エラー種別、発生時刻、影響範囲、スタックトレース、実行パラメータ（クラス名、課題名）
6. WHILE システムが実行されている THE システムは構造化ログ（JSON形式推奨）で以下の情報を出力しなければならない:
   - タイムスタンプ
   - ログレベル（INFO、WARNING、ERROR）
   - 処理フェーズ
   - 処理対象（クラス名、課題名、ファイル名）
   - 実行時間
7. WHEN 処理が正常終了する THEN システムは処理サマリーログ（処理ファイル数、スキップ数、失敗数、実行時間）を出力しなければならない

### 要件8: Cloud Run Functionsでの実行とパラメータ管理
**目的:** システム管理者として、Cloud Schedulerから柔軟にパラメータを渡して複数パターンの処理を実行できるようにすることで、7クラス×複数課題の組み合わせに対応する

#### 受入基準
1. WHEN Cloud Run Function（第2世代）がデプロイされる THEN システムはHTTPリクエストをトリガーとして受け付けなければならない
2. WHEN HTTPリクエストを受信する THEN システムはリクエストボディから以下のパラメータを抽出しなければならない:
   - class_name: クラス名（文字列）
   - task_name: 課題名（文字列）
   - drive_folder_id: Google DriveフォルダID（文字列）
   - spreadsheet_id: スプレッドシートID（文字列）
3. IF 必須パラメータが欠けている THEN システムはHTTP 400エラーを返し、欠けているパラメータ名を示すエラーメッセージを含めなければならない
4. WHEN Cloud Schedulerがジョブを実行する THEN システムは各クラス×課題の組み合わせに対して個別のスケジュールジョブを設定しなければならない
5. WHEN スケジュールジョブが設定される THEN システムは実行タイミングを30分間隔でずらして同時実行を避けなければならない
6. WHEN Functionが実行される THEN システムは実行タイムアウトを適切に設定しなければならない（推奨: 540秒）
7. WHEN Functionが実行される THEN システムはメモリ割り当てを適切に設定しなければならない（推奨: 1GB以上、Playwright要件考慮）
8. WHEN 処理が完了する THEN システムはHTTP 200ステータスと処理結果サマリーをJSONで返さなければならない
9. IF 処理中にエラーが発生する THEN システムはHTTP 500ステータスとエラー詳細をJSONで返さなければならない

### 要件9: トレーサビリティと監査ログ
**目的:** システム管理者として、全ての処理履歴を追跡できるようにすることで、デバッグとメンテナンスを容易にする

#### 受入基準
1. WHEN システムが起動する THEN システムは実行ID（UUID）を生成し、全ログに含めなければならない
2. WHEN 各処理ステップが実行される THEN システムは以下の情報をログに出力しなければならない:
   - 実行ID
   - タイムスタンプ（ISO 8601形式、ミリ秒精度）
   - ログレベル
   - 処理フェーズ名
   - 入力パラメータ
   - 処理結果
   - 実行時間（ミリ秒）
3. WHEN ファイルをダウンロードする THEN システムは以下を記録しなければならない: ファイル名、ファイルサイズ、ダウンロード元URL、ダウンロード開始/終了時刻
4. WHEN Google Drive/Sheetsにデータを書き込む THEN システムは以下を記録しなければならない: 操作種別（作成/更新）、対象リソースID、書き込みデータサマリー、API応答時間
5. WHEN Firestoreにデータを書き込む THEN システムは以下を記録しなければならない: コレクションパス、ドキュメントID、書き込みフィールド数、API応答時間
6. WHILE システムが実行されている THE システムはCloud Loggingに構造化ログを送信しなければならない
7. WHEN 処理が終了する THEN システムは最終サマリーログを出力し、以下の統計情報を含めなければならない: 総処理時間、処理ファイル数、スキップ数、成功数、失敗数、各フェーズの所要時間
