# 実装タスク

## 概要

本タスクドキュメントは、Firestoreスキーマ改善機能の実装を段階的に進めるための詳細なタスクリストです。各タスクは、要件定義書と技術設計ドキュメントに基づいて作成されており、TDD（テスト駆動開発）アプローチに従います。

**実装アプローチ**:
- テストファースト: 各機能の実装前にテストを作成
- 段階的デリバリー: 小さな単位で実装・テスト・検証を繰り返し
- 後方互換性維持: 既存機能を破壊しない
- fail-open戦略継続: 高可用性を優先

**想定工数**: 約8-12時間（テスト含む）

## タスク一覧

### 2. FirestoreServiceクラスの拡張（TDD）

テスト駆動開発アプローチで、FirestoreServiceクラスに親ドキュメント管理機能を追加します。

**要件マッピング**: 要件1（タスク親ドキュメント自動管理）、要件2（ファイル数自動集計）、要件5（後方互換性）

#### 2.1. _update_task_metadataプライベートメソッドのテスト作成

**目的**: 親ドキュメント管理ロジックのテストを先に作成する（TDD）

**作業内容**:
- `tests/unit/test_firestore_service.py` ファイルを作成
- `test_update_task_metadata_creates_new_document` テストケースを作成
  - Firestoreクライアントをモック化
  - 親ドキュメントが存在しない場合の動作を検証
  - `set()` が正しいパラメータ（task_id, task_pattern, file_count=0, created_at, last_updated）で呼ばれることを確認
  - `merge=True` が指定されていることを確認
- `test_update_task_metadata_increments_file_count` テストケースを作成
  - 親ドキュメントが既に存在する場合の動作を検証
  - `Increment(1)` が使用されていることを確認
  - `last_updated` が更新されることを確認
- `test_update_task_metadata_fails_gracefully` テストケースを作成
  - Firestoreエラー発生時のfail-open動作を検証
  - `False` が返されることを確認
  - `logger.error` が呼ばれることを確認

**受入基準**:
- 3つのテストケースが実装されている
- テスト実行時、メソッドが未実装のため失敗する（Red状態）
- テストコードがFirestoreクライアントを適切にモック化している

**想定工数**: 1時間

#### 2.2. _update_task_metadataプライベートメソッドの実装

**目的**: テストをパスする最小限の実装を行う（TDD Green）

**作業内容**:
- `src/firestore_service.py` に `_update_task_metadata` メソッドを追加
- パラメータ: `class_name: str`, `task_id: str`, `task_pattern: str`
- 戻り値: `bool`（成功時True、失敗時False）
- 親ドキュメント参照を取得: `self.db.collection(class_name).document(task_id)`
- `set()` メソッドを使用して以下のフィールドを設定:
  - `task_id`: 受け取った値
  - `task_pattern`: 受け取った値
  - `file_count`: `firestore.Increment(1)`
  - `last_updated`: `firestore.SERVER_TIMESTAMP`
  - 新規作成時のみ: `created_at`: `firestore.SERVER_TIMESTAMP`
- `merge=True` を指定（既存ドキュメントがある場合は更新のみ）
- エラーハンドリング: try-exceptで囲み、エラー時は `logger.error` でログ記録し `False` を返す
- 成功時は `logger.info` でログ記録し `True` を返す

**受入基準**:
- `_update_task_metadata` メソッドが実装されている
- タスク2.1で作成した3つのテストがすべてパスする（Green状態）
- コードがPEP 8スタイルガイドに準拠している
- メソッドにdocstringが追加されている

**想定工数**: 1時間

#### 2.3. record_uploadメソッドへのtask_patternパラメータ追加のテスト作成

**目的**: 既存メソッドの拡張をテスト駆動で進める

**作業内容**:
- `test_record_upload_updates_parent_and_adds_file` テストケースを作成
  - `record_upload` が `_update_task_metadata` を呼び出すことを検証
  - `task_pattern` パラメータが正しく渡されることを確認
  - ファイルドキュメントが正しく作成されることを確認
- `test_record_upload_with_default_task_pattern` テストケースを作成
  - `task_pattern` が省略された場合、`task_id` がデフォルト値として使用されることを確認
- `test_record_upload_continues_on_parent_update_failure` テストケースを作成
  - 親ドキュメント更新失敗時もファイル追加が継続されることを確認（fail-open）

**受入基準**:
- 3つのテストケースが実装されている
- テスト実行時、`task_pattern` パラメータが存在しないため失敗する（Red状態）

**想定工数**: 1時間

#### 2.4. record_uploadメソッドの拡張実装

**目的**: 親ドキュメント管理を統合し、テストをパスさせる（TDD Green）

**作業内容**:
- `record_upload` メソッドのシグネチャに `task_pattern: Optional[str] = None` を追加
- メソッド冒頭で `task_pattern` のデフォルト値を設定: `task_pattern = task_pattern or task_id`
- ファイルドキュメント作成の**前**に `_update_task_metadata` を呼び出す
- `_update_task_metadata` の戻り値に関わらず、ファイルドキュメントの作成を継続（fail-open）
- 既存のロギング戦略を維持（`logger.info` と `logger.error`）

**受入基準**:
- `record_upload` メソッドに `task_pattern` パラメータが追加されている
- タスク2.3で作成した3つのテストがすべてパスする（Green状態）
- メソッドのdocstringが更新されている（新規パラメータの説明を追加）
- 既存の `check_already_uploaded` メソッドに変更がない

**想定工数**: 1時間

#### 2.5. check_already_uploadedメソッドの不変性テスト作成

**目的**: 重複チェックロジックが変更されていないことを保証する

**作業内容**:
- `test_check_already_uploaded_unchanged` テストケースを作成
  - Firestoreクライアントをモック化
  - 既存の重複チェックロジックが正しく動作することを検証
  - サブコレクション（`documents`）のみをクエリし、親ドキュメントには触れないことを確認
  - 重複ファイル検出時、既存レコードを返すことを確認
  - 新規ファイル時、`None` を返すことを確認
  - Firestoreエラー時、`None` を返すことを確認（fail-open）

**受入基準**:
- テストケースが実装されている
- テストがパスする（既存ロジックが変更されていないことを確認）
- 重複チェックの各シナリオ（重複検出、新規、エラー）がカバーされている

### 3. マイグレーションスクリプトの実装（TDD）

既存データから親ドキュメントを生成するマイグレーションスクリプトを作成します。

**要件マッピング**: 要件4（データマイグレーション機能）

#### 3.1. マイグレーションスクリプトの基本構造とテスト作成

**目的**: マイグレーションロジックのテストを先に作成する（TDD）

**作業内容**:
- `tests/unit/test_migrate_parent_documents.py` ファイルを作成
- `test_migrate_class_tasks_creates_parent_documents` テストケースを作成
  - Firestoreクライアントをモック化
  - `documentsサブコレクション` から `task_id` リストを抽出できることを検証
  - 各 `task_id` に対して親ドキュメントが作成されることを確認
  - `file_count` が実際のドキュメント数と一致することを確認
- `test_migrate_skips_existing_parent_documents` テストケースを作成
  - 既に親ドキュメントが存在する場合、スキップされることを確認
- `test_migrate_dry_run_mode` テストケースを作成
  - `dry_run=True` の場合、実際の書き込みが行われないことを確認
  - レポートのみが出力されることを確認

**受入基準**:
- 3つのテストケースが実装されている
- テスト実行時、スクリプトが未実装のため失敗する（Red状態）

**想定工数**: 1時間

#### 3.2. マイグレーションスクリプトの実装

**目的**: マイグレーションロジックを実装し、テストをパスさせる（TDD Green）

**作業内容**:
- `scripts/migrate_parent_documents.py` ファイルを作成
- コマンドライン引数の処理:
  - `--dry-run`: プレビューのみ（デフォルト）
  - `--execute`: 実際にマイグレーションを実行
- `migrate_parent_documents(dry_run: bool)` 関数を実装:
  - KNOWN_CLASSES と KNOWN_TASK_IDS を使用してクラスとタスクをスキャン
  - 各 `{class_name}/{task_id}` に対して:
    - 親ドキュメントが存在するかチェック
    - 存在しない場合、`documentsサブコレクション` をスキャンして `file_count` を計算
    - 親ドキュメントを作成（`task_id`, `task_pattern=task_id`, `file_count`, `created_at`, `last_updated`）
    - Dry-runモードの場合、実際の書き込みはスキップしプレビューを表示
- エラーハンドリング: try-exceptで囲み、エラー発生時は処理を中断しログ出力
- 進捗表示: 処理中のクラス/タスクを標準出力に表示

**受入基準**:
- `scripts/migrate_parent_documents.py` が実装されている
- タスク3.1で作成した3つのテストがすべてパスする（Green状態）
- `--dry-run` と `--execute` の両モードが正しく動作する
- スクリプトがコマンドラインから実行可能

**想定工数**: 1.5時間

#### 3.3. マイグレーション検証ロジックの実装

**目的**: マイグレーション後のデータ整合性を検証する機能を追加する

**作業内容**:
- `validate_migration()` 関数を `migrate_parent_documents.py` に追加
- 各親ドキュメントの `file_count` と実際の `documentsサブコレクション` のドキュメント数を比較
- 不一致がある場合、詳細をレポートに追加:
  - `class_name`
  - `task_id`
  - `expected` (親ドキュメントの `file_count`)
  - `actual` (サブコレクションの実ドキュメント数)
- 検証結果をJSON形式で出力

**受入基準**:
- `validate_migration()` 関数が実装されている
- 不一致検出時、詳細なレポートが出力される
- 検証がマイグレーション実行後に自動的に実行される

**想定工数**: 1時間

#### 3.4. マイグレーションレポート出力機能の実装

**目的**: マイグレーション結果を視覚的に分かりやすく出力する

**作業内容**:
- レポート生成機能を実装:
  - `total_classes`: 処理したクラス数
  - `total_tasks`: 処理したタスク数
  - `created_documents`: 新規作成した親ドキュメント数
  - `skipped_documents`: 既に存在していた親ドキュメント数
  - `validation_errors`: file_count不一致のリスト
- レポートをJSON形式とテキスト形式の両方で出力
- Dry-runモードでは、作成される予定の親ドキュメントをプレビュー表示

**受入基準**:
- レポートが正しいフォーマットで出力される
- JSON形式のレポートファイルが生成される（`migration_report.json`）
- Dry-runモードでプレビューが見やすく表示される

**想定工数**: 45分

### 4. ロールバックとメンテナンススクリプトの実装

#### 4.1. rollback_parent_documents.pyスクリプトの作成

**目的**: マイグレーション失敗時やデプロイロールバック時に親ドキュメントを削除する

**作業内容**:

- 削除前に確認プロンプトを表示（`--confirm` フラグが必要）
- 削除対象のドキュメントリストを表示
- 削除結果をログ出力

**受入基準**:
- スクリプトが実装されている
- `--confirm` フラグなしでは実行されない（安全機構）
- 削除対象が明確に表示される
- サブコレクション（`documents`）は削除されない（保持される）

**想定工数**: 1時間

#### 4.2. fix_file_count.pyスクリプトの作成

**目的**: file_countの不整合を検出・修正するユーティリティを提供する

**作業内容**:
- `scripts/fix_file_count.py` ファイルを作成
- コマンドライン引数の処理:

  - `--task-id`: 対象のタスクID（オプショナル、省略時はすべて）
  - `--dry-run`: プレビューのみ
  - `--execute`: 実際に修正を実行
- 指定されたクラス/タスクの `file_count` と実際のドキュメント数を比較
- 不一致がある場合、`file_count` を正しい値に更新
- 修正内容をログ出力

**受入基準**:
- スクリプトが実装されている
- `--dry-run` で修正対象をプレビューできる
- `--execute` で実際に修正が実行される
- すべてのクラス/タスクを一括修正できる

**想定工数**: 1時間

#### 6.2. マイグレーションスクリプトの本番実行と検証（ステージング環境）

**作業内容**:

**受入基準**:
- マイグレーションが正常に完了する
- 検証レポートにエラーがない
- 親ドキュメントが正しく作成されている

**想定工数**: 1時間

#### 6.3. 新しいコードのデプロイと統合テスト実行（ステージング環境）

### 7. 本番環境へのデプロイとモニタリング

本番環境へのマイグレーションとコードデプロイを実施し、24時間モニタリングを行います。

**要件マッピング**: 要件7（エラーハンドリングとロールバック）、成功基準（本番稼働）

#### 7.1. Firestoreバックアップの確認

**目的**: ロールバックに備えてデータのバックアップを確保する

**作業内容**:
- Google Cloud Consoleで最新のFirestoreバックアップを確認
- バックアップが存在しない場合、手動でエクスポートを実行:
  ```bash
  gcloud firestore export gs://carewell-automation-backup/$(date +%Y%m%d) \
    --database=carewell-native \
    --async
  ```
- エクスポートの完了を確認
- バックアップの保存場所とファイル名を記録

**受入基準**:
- 最新のバックアップが存在する（または作成された）
- バックアップが完全であることを確認
- ロールバック手順にバックアップ情報を記載

**想定工数**: 30分

#### 7.2. 本番環境でのマイグレーション実行

**目的**: 本番データに対してマイグレーションを実行し、親ドキュメントを作成する

**作業内容**:
- マイグレーション実行のタイミングを決定（平日9:00-12:00推奨）
- 関係者にマイグレーション開始を通知
- マイグレーションスクリプトを実行:
  ```bash
  python scripts/migrate_parent_documents.py --execute
  ```
- 実行中の進捗をリアルタイムでモニタリング
- 完了後、検証レポートを確認:
  - 令和7年度 №01/課題① の `file_count` == 20
  - 他のクラス/タスクの `file_count` == 0
  - `validation_errors` が空
- 不一致がある場合、`fix_file_count.py` スクリプトで修正
- 関係者にマイグレーション完了を報告

**受入基準**:
- マイグレーションが正常に完了する
- 検証レポートにエラーがない（または修正済み）
- 既存データが損なわれていない

**想定工数**: 1時間

#### 7.3. 新しいコードの本番デプロイ

**目的**: 親ドキュメント管理機能を本番環境に展開する

**作業内容**:
- 新しいコードを本番のCloud Runにデプロイ:
  ```bash
  gcloud run deploy carewell-file-collector --source . --region asia-northeast1
  ```
- デプロイ完了を確認
- 新しいリビジョンに100%のトラフィックが流れていることを確認
- `test_request.sh` を使用して簡易テストを実行（本番データを使用しない）
- Cloud Runのログを確認:
  - 親ドキュメント更新の成功ログが記録されているか
  - エラーログがないか
- 関係者にデプロイ完了を報告

**受入基準**:
- コードのデプロイが正常に完了する
- Cloud Runの新しいリビジョンが動作している
- 初回テストが正常に動作する
- ログにエラーがない

**想定工数**: 1時間

#### 7.4. 24時間のモニタリングと検証

**目的**: 本番稼働後の問題を早期に検出し、必要に応じてロールバックする

**作業内容**:
- Cloud Runのログを定期的に確認（最初の1時間は15分ごと、その後は1時間ごと）
- 以下のメトリクスをモニタリング:
  - エラー率（目標: 5%未満）
  - レイテンシ（目標: 500ms以内/リクエスト）
  - 親ドキュメント更新の成功/失敗ログ数
  - Cloud Schedulerジョブの実行結果
- Firestore Consoleで `file_count` の正確性を定期的に確認
- 問題が発見された場合の対応:
  - エラー率が5%を超える → ロールバック手順を開始
  - `file_count` に不一致がある → `fix_file_count.py` スクリプトで修正
  - 重複チェックが動作しない → 即座にロールバック
- 24時間経過後、成功基準を確認:
  - エラーゼロであるか
  - すべての機能が正常に動作しているか
  - データ整合性が保たれているか
- 関係者に最終レポートを提出

**受入基準**:
- 24時間エラーゼロで動作する
- すべてのCloud Schedulerジョブが正常に実行される
- `file_count` が正確である
- 重複チェック機能が100%動作する
- ロールバックが不要である

**想定工数**: 24時間（断続的なモニタリング、実作業は合計3-4時間）

## リスク管理

各タスク実行時は以下のリスクに注意してください：

| リスク | 影響 | 緩和策 |
|--------|------|--------|
| マイグレーション中のデータ損失 | 致命的 | 事前バックアップ、dry-run実行、段階的実行 |
| file_count不整合 | 高 | FieldValue.increment使用、修正スクリプト準備 |
| 重複チェック機能の破壊 | 致命的 | 包括的テスト、本番前検証、ロールバック準備 |
| 本番デプロイ後の問題 | 高 | 24時間モニタリング、即座のロールバック体制 |
