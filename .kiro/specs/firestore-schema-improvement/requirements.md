# 要件定義書

## はじめに

本プロジェクトは、carewell-drive-automationシステムのFirestoreデータ構造を改善し、タスク親ドキュメントにメタデータを保存することで、動的な課題管理を可能にします。現在、サブコレクション（documents）のみを使用しているため、フロントエンドで課題IDをハードコードする必要があり、拡張性に制約があります。

本改善により、Firestoreのベストプラクティスに準拠した階層構造を実現し、将来的な機能拡張（新課題追加、締切管理等）の基盤を構築します。**重要な制約として、既存の重複チェック機能を100%維持し、運用中のシステムに影響を与えないことが求められます。**

**ビジネス価値**:
- フロントエンド開発効率の向上（課題追加時のコード変更不要）
- データ構造のセオリー準拠による保守性向上
- 将来的な機能拡張の基盤整備

## 要件

### 要件1: タスク親ドキュメント自動管理

**Objective**: システム管理者として、ファイルアップロード時にタスク親ドキュメントが自動的に作成・更新されることで、手動でのデータ構造管理が不要になることを期待する

#### 受入基準

1. WHEN FirestoreServiceがrecord_uploadメソッドを呼び出す THEN システムは指定されたclass_nameとtask_idに対応する親ドキュメントを作成または更新しなければならない

2. IF タスク親ドキュメントが存在しない THEN システムは以下のフィールドを持つ新しいドキュメントを作成しなければならない:
   - task_id (string): タスク識別子（例: "課題①"）
   - task_pattern (string): タスク検索パターン（例: "課題①業務分析　※～11/3〆切"）
   - file_count (number): 初期値0
   - created_at (timestamp): ドキュメント作成日時
   - last_updated (timestamp): 最終更新日時

3. IF タスク親ドキュメントが既に存在する THEN システムはlast_updatedフィールドのみを現在時刻で更新しなければならない

4. WHEN 親ドキュメント作成または更新が失敗する THEN システムは詳細なエラーログを記録し、呼び出し元にFalseを返さなければならない

5. WHERE 複数のファイルが同時にアップロードされる THE システムは親ドキュメントのfile_countフィールドに対してFirestore FieldValue.increment()を使用してアトミックに更新しなければならない

### 要件2: ファイル数自動集計機能

**Objective**: システム管理者として、タスクごとのファイル数が自動的に集計されることで、手動集計作業が不要になり、ダッシュボードでリアルタイムに統計情報を表示できることを期待する

#### 受入基準

1. WHEN 新しいファイルがdocumentsサブコレクションに追加される THEN システムは親ドキュメントのfile_countをFirestore FieldValue.increment(1)で増加させなければならない

2. WHEN ファイル追加処理が成功する AND 親ドキュメント更新も成功する THEN システムはfile_countが正確にインクリメントされたことをログに記録しなければならない

3. IF file_countの更新が失敗する THEN システムはエラーログを記録するが、既存のfail-open戦略に従いファイル追加処理自体は成功として扱わなければならない

4. WHEN マイグレーション実行時 THEN システムは既存のdocumentsサブコレクション内のドキュメント数をカウントし、親ドキュメントのfile_countに正確に設定しなければならない

5. WHERE 並行アップロード（複数リクエスト同時実行）が発生する THE システムはFieldValue.increment()のトランザクショナル特性により、file_countの整合性を保証しなければならない

### 要件3: 重複チェック機能の完全維持

**Objective**: システム運用者として、既存の重複チェック機能が100%動作し続けることで、本番環境での動作に影響を与えないことを期待する

#### 受入基準

1. WHEN FirestoreServiceのcheck_already_uploadedメソッドが呼び出される THEN システムは既存のロジック（composite_keyによるドキュメント存在チェック）を完全に維持しなければならない

2. IF サブコレクション（documents）内にcomposite_keyと一致するドキュメントが存在する THEN システムはそのドキュメントのデータを返し、「既にアップロード済み」と判定しなければならない

3. IF サブコレクション内にcomposite_keyと一致するドキュメントが存在しない THEN システムはNoneを返し、「新規アップロード」と判定しなければならない

4. WHEN 重複ファイルを検出する THEN システムは親ドキュメントのfile_countを増加させず、スキップ処理を実行しなければならない

5. WHERE 重複チェック中にFirestoreエラーが発生する THE システムは既存のfail-open戦略に従い、Noneを返してアップロードを許可しなければならない

### 要件4: データマイグレーション機能

**Objective**: システム管理者として、既存の20件のファイルデータを損失なく新しいスキーマに移行できることで、データ整合性を保証しつつ本番環境に適用できることを期待する

#### 受入基準

1. WHEN マイグレーションスクリプトを実行する THEN システムは全クラス・全タスクのdocumentsサブコレクションをスキャンし、親ドキュメントが存在しない場合は作成しなければならない

2. IF 親ドキュメントをマイグレーション作成する THEN システムは以下の値を設定しなければならない:
   - task_id: サブコレクション内の最初のドキュメントのtask_idフィールドから取得
   - task_pattern: task_idと同じ値を設定（後で手動更新可能）
   - file_count: サブコレクション内のドキュメント総数
   - created_at: マイグレーション実行時の現在時刻
   - last_updated: マイグレーション実行時の現在時刻

3. WHEN マイグレーション実行前 THEN システムはFirestoreのバックアップを自動で作成するか、管理者にバックアップを促す警告メッセージを表示しなければならない

4. WHEN マイグレーション実行中にエラーが発生する THEN システムは処理を中断し、どのクラス・タスクまで処理が完了したかをログに記録し、ロールバック手順を提示しなければならない

5. WHEN マイグレーション完了後 THEN システムは各タスクのfile_countとdocumentsサブコレクション内の実際のドキュメント数を比較し、整合性を検証しなければならない

6. IF マイグレーション検証で不一致が検出される THEN システムは不一致の詳細（class_name, task_id, expected, actual）をレポートに出力しなければならない

### 要件5: 後方互換性の保証

**Objective**: システム運用者として、Cloud Schedulerの設定やHTTPリクエストペイロードを変更せずに新しいスキーマが動作することで、デプロイリスクを最小化できることを期待する

#### 受入基準

1. WHEN 既存のCloud Schedulerジョブが実行される THEN システムは既存のHTTPリクエストペイロード（class_name, task_id, task_pattern, drive_folder_id, spreadsheet_id）を受け入れ、正常に処理しなければならない

2. IF HTTPリクエストにtask_patternが含まれている THEN システムは親ドキュメント作成時にそのtask_patternを使用しなければならない

3. IF HTTPリクエストにtask_patternが含まれていない THEN システムはtask_idと同じ値をtask_patternとして使用しなければならない

4. WHEN 新しいコードをCloud Runにデプロイする AND テスト実行前 THEN システムは既存の14個のCloud Schedulerジョブ設定を変更してはならない

5. WHERE documentsサブコレクションの構造に関して THE システムは既存のフィールド（composite_key, task_id, student_name, student_id, filename, drive_file_id, drive_folder_id, submit_date, uploaded_at, metadata）を一切変更してはならない

### 要件6: テストカバレッジと品質保証

**Objective**: 開発者として、包括的なテストスイートにより機能の正確性と回帰防止が保証されることで、安心してデプロイできることを期待する

#### 受入基準

1. WHEN ユニットテストを実行する THEN システムは以下の機能をカバーしなければならない:
   - 親ドキュメントの新規作成
   - 既存親ドキュメントの更新
   - file_countのインクリメント
   - 重複チェックロジック
   - エラーハンドリング

2. IF ユニットテストが失敗する THEN システムはCI/CDパイプラインでデプロイを中断しなければならない

3. WHEN 統合テストを実行する THEN システムはtest_request.shを使用して以下のシナリオを検証しなければならない:
   - 新規ファイルアップロード → 親ドキュメント作成 + file_count=1
   - 2件目のファイルアップロード → file_count=2に更新
   - 重複ファイルアップロード試行 → スキップ + file_count変化なし
   - マイグレーション実行 → 既存20件のfile_count正確性

4. WHEN 統合テスト実行後 THEN システムはFirestoreの状態を検証し、以下を確認しなければならない:
   - 親ドキュメントが正しく作成されている
   - file_countが実際のドキュメント数と一致している
   - documentsサブコレクションが損なわれていない

5. WHERE テスト環境とステージング環境が存在する THE システムは本番デプロイ前に両環境でテストを実行し、成功を確認しなければならない

### 要件7: エラーハンドリングとロールバック

**Objective**: システム運用者として、エラー発生時に適切なログ記録とロールバック手順が提供されることで、迅速な復旧が可能になることを期待する

#### 受入基準

1. WHEN 親ドキュメント作成に失敗する THEN システムは以下の情報をログに記録しなければならない:
   - エラーメッセージ
   - スタックトレース
   - class_name
   - task_id
   - タイムスタンプ

2. IF マイグレーション中にエラーが発生する THEN システムは処理を中断し、以下を提供しなければならない:
   - 処理完了したクラス・タスクのリスト
   - エラーが発生したクラス・タスク
   - ロールバック用のFirestoreクエリ（親ドキュメント削除）

3. WHEN 本番デプロイ後に問題が発見される THEN システム管理者は以下の手順でロールバックできなければならない:
   - 以前のCloud Runリビジョンに切り戻し
   - 親ドキュメントを削除（documentsサブコレクションは保持）
   - 動作確認

4. IF file_countの不整合が検出される THEN システムは修正スクリプトを提供し、documentsサブコレクションを再カウントしてfile_countを修正できなければならない

5. WHERE Firestore操作がタイムアウトする THE システムは最大3回までリトライを実行し、それでも失敗する場合はエラーログを記録して呼び出し元に失敗を通知しなければならない

## 非機能要件

### パフォーマンス

1. WHEN 親ドキュメント作成または更新を実行する THEN システムは100ms以内に完了しなければならない

2. IF 並行アップロード（最大5リクエスト同時）が発生する THEN システムはfile_countの整合性を保ちながら、各リクエストを500ms以内に処理しなければならない

### スケーラビリティ

1. WHEN 課題数が増加する（現在の2課題から10課題へ） THEN システムは追加の親ドキュメントを自動的に管理し、パフォーマンス劣化なく動作しなければならない

2. IF クラス数が増加する（現在の7クラスから20クラスへ） THEN システムはFirestoreのコレクション構造を拡張でき、クエリパフォーマンスを維持しなければならない

### セキュリティ

1. WHERE 親ドキュメントにメタデータを保存する THE システムは機密情報（学生の個人情報、認証情報等）を含めてはならない

2. WHEN Firestoreセキュリティルールを設定する THEN システムは読み取り専用アクセス（allow read: if true）を許可し、書き込みを禁止（allow write: if false）しなければならない

### 保守性

1. WHEN コードにドキュメント文字列を追加する THEN システムは各メソッドの目的、引数、戻り値、例外を明記しなければならない

2. IF 将来的に親ドキュメントにフィールドを追加する THEN システムは既存コードを破壊せず、後方互換性を保ちながら拡張できなければならない

## 制約条件

### 技術的制約

- Firestore Native Modeデータベース（carewell-native）を使用
- Python 3.11+環境での実装
- google-cloud-firestore SDKを使用
- 既存のfirestore_service.pyファイルを修正（新規ファイル作成不可）

### ビジネス制約

- デプロイは日本時間の平日9:00-17:00のみ許可
- 本番環境でのテストは禁止（ステージング環境で完全検証後にデプロイ）
- ダウンタイムなしでのデプロイが必須

### スコープ制約

- フロントエンド（carewell-dashboard）の修正は本要件のスコープ外
- 既存の14個のCloud Schedulerジョブ設定変更は不可
- Firestore (default)データベースは対象外（carewell-nativeのみ）

## 成功基準

プロジェクトは以下の基準をすべて満たした場合に成功と見なされます：

1. **機能完全性**: 全7要件の受入基準を100%満たす
2. **テストカバレッジ**: ユニットテスト80%以上、統合テスト100%
3. **データ整合性**: マイグレーション後のfile_count検証で不一致ゼロ
4. **重複チェック維持**: 既存の重複チェックロジックが100%動作
5. **後方互換性**: Cloud Scheduler設定変更なしで動作
6. **本番稼働**: 本番デプロイ後24時間エラーゼロ

## リスク分析

### 高リスク

| リスク | 影響 | 緩和策 |
|--------|------|--------|
| マイグレーション中のデータ損失 | 致命的 | 事前バックアップ、段階的実行、検証ステップ |
| file_count不整合 | 高 | トランザクション使用、修正スクリプト準備 |
| 重複チェック機能の破壊 | 致命的 | 包括的テスト、本番前検証 |

### 中リスク

| リスク | 影響 | 緩和策 |
|--------|------|--------|
| 並行アップロード時の競合 | 中 | FieldValue.increment()使用、テスト実施 |
| Cloud Runタイムアウト | 中 | 親ドキュメント操作の高速化、リトライ実装 |

### 低リスク

| リスク | 影響 | 緩和策 |
|--------|------|--------|
| フロントエンドとの連携遅延 | 低 | 段階的実装、後方互換性保証 |
